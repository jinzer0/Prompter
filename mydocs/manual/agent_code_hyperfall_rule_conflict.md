# Claude와 Codex 기본 동작과 하이퍼-워터폴 충돌 규칙

## 목적

Claude와 Codex는 기본적으로 빠른 실행과 자율 수정에 최적화되어 있다. 이 프로젝트는 하이퍼-워터폴 방법론을 적용하므로, 기본 동작이 프로세스 규율과 충돌할 수 있다. 이 문서는 충돌 시 우선순위와 처리 기준을 정의한다.

## 충돌 지점

1. 자율 실행 vs 위험 결정/행동 승인
2. 필요한 기존 계획·Evidence를 무시한 코드 우선 수정
3. 타스크 종료/이슈 클로즈의 성급한 처리
4. 작업 범위 확장(관련 리팩터링, 불필요 생성물 갱신)

## 우선순위 규칙

1. 작업지시자 명시 지시
2. `AGENTS.md` 강제 규칙
3. task 문서(`plans`, `working`, `report`, `orders`)
4. 자동화 도구/에이전트 기본 동작

상위 규칙과 충돌하면 하위 규칙을 적용하지 않는다.
이는 저장소 내부 우선순위이며 시스템/플랫폼 지침과 Tool Permission을 대체하지 않는다. Prompter 고유 보안·아키텍처·UI·테스트 규칙은 `AGENTS.md`의 운영 규칙보다 우선한다.

## 운영 규칙

- 위험은 파일 수·줄 수·Stage 완료가 아니라 영향·가역성·보안·데이터·외부 부작용으로 판단한다. `AGENTS.md`의 위험 기반 정책을 따른다.
- **LOW**는 사전/계획 승인 없이 수행하고 검증·결과·제약을 보고한다. 작은 독립 LOW에는 새 Issue·브랜치·오늘할일·계획/보고 파일·PR·형식 Stage를 강제하지 않는다. 기존 Issue가 있으면 연결하고 명시 요청된 산출물은 작성한다.
- **MEDIUM**은 명확한 목표·대상·수용 기준·제약을 포함한 요청 자체가 Scope 승인이다. 범위 내 계획·구현·테스트·리뷰·수정·기록·Stage 전환은 응답 대기 없이 진행하며 핵심 요구가 불명확하면 해당 결정만 질문한다.
- **HIGH**인 중대한 구조·보안·인증/권한·호환성 파괴·데이터 삭제·파괴적 migration·운영 배포·중대한 외부 영향·고비용·큰 Scope 이탈은 해당 결정/행동 직전 명시 승인받는다. 미승인/거절 행동과 그 의존 작업만 보류하고 독립 안전 작업은 계속한다. 침묵·auto 모드·Stage 완료는 승인이 아니다.
- 필요한 추적 작업은 `이슈 -> 브랜치 -> 오늘할일 -> 계획 -> 구현 -> 검증 -> 결과 보고 -> PR` 중 규모·위험·의존성에 필요한 절차만 적용한다. Stage 수에 고정 최소/최대 수를 두지 않는다.
- 충분한 기존 계획과 승인 기록을 참조·보완하며 같은 계획이나 동일 결정 승인을 재생성하지 않는다. BMAD는 의도·요구·설계·수용 기준·적정 계획, Hyper-Waterfall은 실행·상태·영속화·Evidence·검증·인계를 담당한다.
- Checkpoint는 비차단 상태·검증·Evidence·인계 기록이며 Human Approval은 특정 위험 결정/행동의 명시 동의다. 승인 결정·범위·근거·결과를 기존 기록에 남긴다. 둘 다 실제 차단이나 정상 종료 HALT를 대신하지 않는다.
- 테스트 실패는 Scope 안에서 자율 수정·재검증한다. 기존 finite safety cap·영속 counter·동일 실패 resume 누적을 유지한다. 기존 counted review loop의 >5는 blocked 원인·triage·검증 미완료 Evidence를 남기고 추가 loopback 전에 종료한다. plan 삭제·counter reset·상태 변경으로 우회하거나 built로 위장하지 않는다.
- 결과 기록은 비차단이며 local commit·원격 게시·PR·Merge·Release·강제 Git 작업과 플랫폼 Tool Permission은 별도다. 기록 작성이나 Scope 승인이 기존 Git 권한을 확대하지 않는다.
- unrelated dirty/untracked 자체는 차단 사유가 아니다. 실제 변경 겹침·소유권 분리 불가·branch/필요 권한/metadata 충돌만 해당 작업을 보류한다. baseline과 변경 전 내용을 바탕으로 자기 diff만 검토·재생성·revert하고 허용된 자기 변경만 commit한다. 사용자/다른 작업자 변경을 되돌리지 않으며 전체 clean tree를 정상 종료 조건으로 강제하지 않는다.
- 이슈 close는 작업지시자 승인 또는 PR merge 이후에만 수행한다.
- 문서 수정은 기존 내용을 먼저 읽고 필요한 부분만 수정하며, 불가피할 때만 내용을 추가한다.
- 문서 위치/독자 판단은 기존 계획/결과에 비차단으로 기록한다. 새 공식 문서 루트 채택 등 큰 Scope 변경은 승인받으며 위치·파일명 규칙과 기존 lifecycle 승인은 유지한다.
- 다음 작업에 필요하지 않은 자기 로컬/원격 부산물은 기존 Git 권한과 정리 절차 안에서 정리한다. 사용자 설치나 다른 작업자의 파일은 부산물로 취급하지 않는다.

## 실무 체크리스트

- 수정 전: 위험·Scope·실제 충돌과 기존 이슈/계획/승인 기록 확인. 작은 독립 LOW에는 없는 기록을 만들도록 강제하지 않음
- 수정 중: 변경 범위가 승인된 요구와 일치하는지 점검
- 수정 후: 검증 결과·제약 보고, 필요한 기존 기록 갱신. PR을 실제 게시하면 본문에 결과 반영, merge 후 기존 권한에 따라 부산물 정리

## 예외 처리

- 작은 독립 LOW는 검증·결과 보고만으로 충분하다. 기존 GitHub Issue가 있으면 결과에 연결하되 새 보고 파일이나 PR을 일률 강제하지 않는다.
- 명시 요청된 산출물과 기존 lifecycle·게시·merge 권한은 위험 기반 절차 축소와 무관하게 준수한다.
