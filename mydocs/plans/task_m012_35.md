# Task #35 수행계획서 — Prompter v0.1.2 macOS ARM64 서명·공증 및 배포

GitHub Issue: [#35](https://github.com/jinzer0/Prompter/issues/35)
마일스톤: M012

## 목적

#31 네이티브 UX·테마 개선과 #26 최신 통합 검증이 반영된 Prompter를 v0.1.2 macOS ARM64 릴리스로 준비한다. 버전 정합성, 회귀, 서명·공증·stapling, 설치 확인을 실제 근거로 검증하고 별도 공개 승인 후 동일한 산출물을 게시한다.

이슈 생성 및 task-start 승인은 제품 수정·Apple 제출·태그 생성·공개 배포 승인이 아니다. 각 단계의 실행과 게시 승인 경계를 유지한다.

## 배경

- 최신 공개 릴리스는 v0.1.1이다. #31/PR #32 및 #26/PR #34가 master에 병합됐다.
- #26의 typecheck/lint/Vitest 1182개 및 fresh build/Electron 65개 통과는 선행 근거다. 버전 변경 후 검증을 대체하지 않는다.
- 최초 worktree 기준선은 `3a456a610eb1c57a3ce86a821bb5390328cf2fa5`다. 원본 checkout의 master와 BMAD/미추적 데이터는 보존한다.
- `package.json`, release-version-preflight와 release-support의 versionFrom은 현재 정확한 0.1.1을 요구한다. signed coordinator는 package version으로 candidate/evidence 경로 및 ZIP/DMG 이름을 구성한다.
- 기존 배포/QA 안내는 0.1.1 및 과거 #6/#7 게시 경계를 포함한다. 새 준비와 기존 공개 릴리스의 사실을 구분해야 한다.
- 작업지시자는 열린 의존성 PR #29/#30/#33 검토를 나중으로 미루고 v0.1.2 배포 task를 먼저 진행하도록 지정했다. 의존성 취약점 해소를 주장하지 않는다.

## 범위

### 포함

- package.json/package-lock.json의 프로젝트 버전 0.1.2 정합성.
- 기존 signed-release preflight와 coordinator의 정확한 허용 버전을 0.1.2로 갱신하고 버전 경계 회귀를 반영한다.
- signed-release 계약/fixture의 version, candidate/evidence path, 파일명 기대값 갱신. 일반 패키징 테스트의 임의 예제 버전은 용도를 확인하여 불필요하게 일괄 변경하지 않는다.
- 기존 native:node/native:electron 스크립트를 사용하는 typecheck/lint/전체 Vitest/fresh build/전체 Electron smoke.
- clean committed ARM64 worktree의 기존 signed coordinator를 통한 실제 Apple preflight·서명·app/DMG 공증·stapling·Gatekeeper·체크섬 검증.
- 격리 설치·실행 확인, app plist 버전/identity와 최종 ZIP/DMG/체크섬 allowlist 검증.
- 기존 공식 release/QA 안내 및 README의 준비/공개 상태 정합성. 실제 릴리스 노트는 GitHub Release 본문에 작성한다.
- 각 단계 보고와 최종 보고, 승인된 구현 PR 게시/merge, 별도 승인된 immutable tag 및 GitHub Release 게시.

### 제외

- 의존성 PR 변경/merge, audit fix, 새 dependency 추가.
- 새 기능·UX 재설계·IPC/DB schema/migration 변경.
- x64/Intel·다른 OS 배포.
- 기존 v0.1.0/v0.1.1 tag/Release/산출물 재작성·교체.
- unsigned fallback을 공개 signed 릴리스로 대신하는 작업.
- 서명 identity·notary profile 값·인증서/private key·환경 전체 dump의 문서/로그/이슈 노출.
- 사용자 DB·설치 앱·BMAD·다른 작업자의 파일 삭제 또는 덮어쓰기.

## 설계 방향

- 기존 exact-version gate만 0.1.2로 갱신한다. 다중 버전 호환 경로·새 release 설정 저장소·기존 버전 fallback을 추가하지 않는다.
- 버전/필수 입력 오류는 build/native rebuild/Apple 명령/candidate 생성 전에 거절한다. coordinator의 ARM64·clean worktree·경로 소유권·symlink·서명·notary·재개/중복 제출·artifact drift 경계를 유지한다.
- 최종 candidate는 `release/v0.1.2/`의 `Prompter-0.1.2-mac-arm64.zip`, `Prompter-0.1.2-mac-arm64.dmg`, `SHA256SUMS`만 허용한다. 실제 생성 전 존재/소유권을 확인하고 기존 디렉터리를 임의 삭제하지 않는다.
- app과 DMG는 별도 Accepted 및 warning/error 없는 Apple log를 확인한다. timeout/재개는 기존 artifact-bound 경로를 사용하고 같은 bytes를 무조건 재제출하지 않는다.
- 단계별 문서를 commit한 뒤 source clean 상태로 실행한다. 후보 생성 전에 source SHA를 고정하고 이후 제품/테스트/의존성 변경 시 기존 후보를 재사용하지 않는다.
- 공개 tag는 검토·병합된 이력에 포함된 실제 후보 source commit을 정확히 가리킨다. 후보를 만든 commit과 이후 보고 문서 commit/merge SHA를 혼동하지 않는다. 공개 직전 승인된 tag 대상, source tree, 후보 SHA256를 재확인한다.
- 공개 게시 전에는 README 설치 안내가 실제 최신 v0.1.1을 유지한다. v0.1.2를 이미 다운로드/설치 가능한 것으로 선행 표기하지 않는다. 공개 후에만 최신 설치 안내를 갱신한다.
- GitHub Release assets는 검증한 bytes 그대로 게시하고 다운로드한 assets의 checksum까지 확인한다. 공개 승인 없이는 tag/create/upload/latest 전환을 수행하지 않는다.

## 잠정 단계

### Stage 1 — v0.1.2 버전·배포 계약 준비

- 구현계획 승인 후 버전 gate, lockfile 및 signed fixture/회귀 갱신.
- maintainer release/QA 안내의 준비 버전과 게시 경계 정합화. 공개 설치 버전은 유지.
- 잘못된 버전/입력, ARM64 제한, 기존 재개/소유권 경계의 focused 회귀 및 보고.

### Stage 2 — 전체 회귀와 배포 기준선 고정

- typecheck/lint/전체 Vitest/fresh build/전체 Electron smoke 실행.
- source SHA/버전 및 실제 검증 결과를 고정하고 candidate 생성 가능 상태를 보고.
- unsigned/dev smoke를 실제 서명/공증/설치 검증으로 확대하지 않는다.

### Stage 3 — 실제 서명·공증 및 격리 설치 검증

- 별도 Stage 3 승인 후 clean worktree, Xcode, Keychain, 두 필수 release 입력과 Apple 연결의 가용성을 비밀값 없이 확인한다.
- 기존 `npm run package:release:macos`로 후보를 생성하고 기존 fail-closed 검증을 통과시킨다.
- 두 notary Accepted, signing/stapling/Gatekeeper/allowlist/checksum 및 격리 설치·실행 근거를 보고한다.
- 사용자 손동작이 필요한 확인은 별도 요청하고 자동화 성공으로 대체하지 않는다.

### Stage 4 — 공개 승인·게시 및 안내 완료

- 후보 검증 최종 보고, 구현 PR 게시/merge 및 실제 배포를 각각 승인받는다.
- 공개 승인 대상 source SHA/tag/assets/SHA256를 대조한 뒤 v0.1.2 tag/Release/assets를 게시한다.
- 공개 조회/다운로드 checksum 확인 후 README 최신 설치 안내를 갱신하고 승인된 문서 게시 절차를 따른다.
- 최종 보고/오늘할일/Issue 완료 및 작업 부산물 정리는 승인/실제 merge·공개 확인 후 수행한다.

## 검증 계획

### 단계별 검증

- Stage 1: signed-release version gate 및 coordinator의 relevant focused tests, `git diff --check`. 거절 시 외부 명령/파일 mutation이 없음을 검증한다.
- Stage 2: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` 성공 후 `npm run test:smoke`, source/lockfile scope audit.
- Stage 3: 기존 signed command와 docs/qa-checklist의 실제 codesign/notary/stapler/Gatekeeper/ZIP 추출/DMG readonly mount/plist/`SHA256SUMS` 확인. 기존 allowlist와 sanitized receipt 유지.
- Stage 4: GitHub tag target, Release 상태/asset 이름·수·크기 및 다운로드 checksum 실제 조회, README의 설치 파일명·상태 대조.

### 통합 수용 기준

- 정확한 v0.1.2 gate와 필수 입력/ARM64/보안·소유권 경계를 유지한다.
- fresh source/build의 회귀 결과, 실제 Apple-backed 후보 검증, 설치 확인, 게시 근거를 분리하여 보고한다.
- 공개 tag/source commit/asset bytes/checksum이 승인된 후보와 일치한다.
- 기존 태그/릴리스·사용자 worktree/DB/BMAD 자료를 보존한다.
- `git diff --check`가 통과하고 release 실행 전/PR 준비 전 git status가 clean이다.

## 리스크

- **미해결 의존성 위험**: PR #29/#30/#33은 보류다. 기존 GitHub 취약점 경고를 유지하고 안전성/해소를 주장하지 않는다. 실제 공개 승인 때 위험을 다시 제시한다.
- **Apple 접근/인증 차단**: Keychain 잠금·identity/profile 부재·네트워크·공증 실패는 우회하지 않고 원인만 비밀값 없이 보고한다. 필요한 사람의 조치를 요청한다.
- **immutable source 불일치**: 후보 생성 후 변경/merge를 동일 SHA로 간주하지 않는다. source tree와 승인 대상 commit/bytes를 확인하고 제품 변경이 있으면 재검증한다.
- **public 안내 조기 변경**: 준비 중에는 공개 최신 v0.1.1 사실을 유지하고 v0.1.2 게시 확인 후 전환한다.
- **실제 사용자 데이터 손상**: QA는 격리 app/임시 데이터로 수행한다. Applications의 기존 앱을 덮어쓰기 전에 명시 승인을 받는다.
- **기존 경고**: native/Vite/Biome/npm 경고는 유지·보고한다. 경고 억제나 install script 허용 정책 완화로 성공을 만들지 않는다.

## 승인 요청 사항

- 이 수행계획의 범위·문서 위치·4단계 및 각 단계 승인 경계를 승인하고 구현계획서 작성을 허용한다.
- v0.1.2 exact-version 준비와 기존 경계 회귀 갱신 방향을 승인한다. 실제 제품 수정은 구현계획/Stage 1 실행 승인 이후다.
- 서명·Apple 제출은 Stage 3, tag/Release/upload는 Stage 4의 별도 승인 이후만 수행한다.
- 의존성 PR은 범위 밖이며 실제 공개 승인 시 미해결 위험을 다시 확인한다.
