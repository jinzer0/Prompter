# `plans/` 폴더 규칙

## 목적

내부 task의 Scope, 설계 방향과 필요한 구현 단계를 정리한다.

## 답하는 질문

- "무엇을 할 것인가?"
- "어떻게 나눠서 구현할 것인가?"
- "무엇이 범위 밖인가?"

## 작성 시점

`AGENTS.md`의 위험 기반 정책에 따라 계획이 필요한 작업에서 작성한다.
BMAD의 충분한 기존 계획을 참조·보완하며 같은 계획이나 승인 문서를 재생성하지 않는다.
명확한 LOW/MEDIUM 요청은 해당 Scope 승인으로, 범위 내 계획·구현·검증·수정·기록은
응답 대기 없이 진행한다. HIGH 결정/행동이나 큰 Scope 변경만 직전에 명시 승인하며
같은 결정의 기존 승인 기록을 재사용한다.

작은 독립 LOW는 검증·결과/제약 보고로 충분하다. 새 Issue·브랜치·계획 파일·형식
Stage를 강제하지 않으며, 기존 Issue가 있으면 연결하고 명시 요청된 산출물은 작성한다.
새 계획이 필요할 때 `task-start`에서 수행계획을 작성하고 필요한 구현 세부사항을 보완한다.
단계 수는 위험·복잡도·의존성에 비례하며 고정 최소/최대를 두지 않는다.

## 허용 파일명

- `task_{milestone}_{이슈번호}.md`
- `task_{milestone}_{이슈번호}_impl.md`

완료된 계획서 보관이 필요하면 `plans/archives/`를 사용한다.

## 사용 템플릿

- `mydocs/_templates/task_plan.md`
- `mydocs/_templates/task_impl_plan.md`

## 반드시 포함할 내용

- 목적
- 배경
- Scope (목표·대상·수용 기준·제약, 포함·제외)
- 충분한 기존 계획과 필요한 기록의 참조 (존재하는 기록만 연결)
- 설계 방향
- 예상 변경 파일
- 필요한 단계 (형식 Stage는 선택)
- 검증 계획
- 리스크
- 필요한 HIGH 결정/행동 승인 사항과 기존 승인 근거 (해당 시)

## 두면 안 되는 내용

- 단계별 완료 보고서
- 최종 보고서
- 실제 구현 후 검증 로그만 모은 문서

## 다음 세션 AI가 복원해야 할 맥락

요청으로 승인된 Scope, 기존 계획·결정 승인 근거, 필요한 단계, 검증 명령,
커밋 메시지 기준. 계획 작성은 local commit·원격 게시·PR·merge 권한을 부여하지 않는다.
