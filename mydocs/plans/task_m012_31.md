# M012 macOS 네이티브 UX/UI 리팩토링 수행계획서

GitHub Issue: [#31](https://github.com/jinzer0/Prompter/issues/31)
마일스톤: M012
상태: Stage 1–5 구현·자동 검증·사용자 OS 확인·최종 보고 승인 완료. [Open PR #32](https://github.com/jinzer0/Prompter/pull/32) 게시 완료

## 목적

웹페이지처럼 느껴지는 Prompter를 창과 작업 영역이 자연스럽게 연결된 macOS 데스크톱 앱으로 개선한다. Electron·React와 필수 Library 3패널을 유지하며 Scratch의 창 통합·절제된 도구 영역·콘텐츠 중심 구성을 참고한다. Scratch 기능이나 기술 스택을 복제하지 않는다.

핵심 사용 흐름은 프롬프트 목록에서 찾기 → 선택 → 직접 복사 또는 수정 → 새 버전 저장이다. 복제해서 저장은 별도 명시적 동작으로 제공한다. 라이트·다크 테마를 동등하게 지원한다.

## 배경

사용자는 타이틀바와 본문의 단절, 웹 UI 같은 외형, 창을 움직일 때의 웹브라우저 같은 느낌을 지적했다. 소스 조사에서 다음을 확인했다.

- `app-shell.tsx`: 외곽 24px 여백, 패널 사이 간격, 패널 모서리·그림자 및 전체 작업 영역 가로 스크롤.
- `window-options.ts`와 `styles.css`: 초기 너비 1024px에 비해 콘텐츠 최소 너비 1040px이며 외곽 여백도 존재.
- `styles.css`: 다크 색상과 `color-scheme: dark` 고정.
- `app-shell.tsx`와 `settings-panel.tsx`: 좁은 사이드바에 탐색·설정·키 관리·유지보수·백업 혼재.
- `prompt-compiler-form.tsx`: 여러 큰 입력란이 연속 배치됨.
- Library와 Settings: Phase 9, Bridge status, DB-backed, SQLite 등 개발 표현 노출.

이는 소스 기반 조사이며 실제 앱 실행·드래그 재현은 아직 하지 않았다. `hiddenInset` 적용 이슈 #14는 닫혔고 #26은 통합 검증 전용이므로 새 구현 범위는 #31로 분리한다.

기존 DESIGN.md는 다크 우선·좁은 창 가로 스크롤을 의도적으로 규정한다. 이번 사용자의 라이트·다크 지원 및 가로 넘침 해소 요구에 맞춰 해당 기준을 명시적으로 개정하는 승인을 요청한다. 3패널·접근성·보안 규칙은 완화하지 않는다.

## 범위

### 포함

- 카드형 외곽 여백·간격·그림자를 정리하고 3패널을 창 내부에 연결한다.
- macOS 창 버튼·타이틀바·툴바·사이드바의 정렬과 배경을 통합한다.
- 초기 창 크기와 최소 콘텐츠 크기의 불일치를 해소한다. 지원 최소 크기와 기존 900x720·1280x800 smoke의 처리 기준은 설계 검증 후 확정한다.
- 시스템 / 라이트 / 다크 선택, 기본 시스템 추종, OS 변경 즉시 반영, 직접 선택 재시작 후 유지.
- 사이드바는 탐색 중심으로 정리하고 설정·키 관리·유지보수·백업은 별도 설정 화면으로 분리한다. Library 복귀 시 선택·편집 상태를 보존한다.
- 컴파일러 핵심 입력과 추가 옵션을 구분하되 기존 기능과 데이터는 제거하지 않는다.
- 개발 내부 표현을 사용자 작업 중심 문구로 교체한다.
- 실제 창 드래그 동작을 검증하고 원인에 맞게 수정한다. 원인을 사전에 단정하지 않는다.
- 컴파일 없이 선택한 프롬프트 직접 복사·수정. 기본 저장과 Cmd+S는 기존 프롬프트의 새 버전 저장, 복제해서 저장은 추가 버튼 동작.
- 다른 프롬프트 선택·창 닫기 시 저장 / 변경 버리기 / 취소로 미저장 변경 보호. 저장 실패 시 내용 유지 및 이동·닫기 중단.
- 기존 macOS 메뉴·단축키, Insights·Privacy의 명시적 작업 원칙과 상태 보존, 잠금·시크릿 보안 유지.
- bmad-ux 시각·행동 계약, 핵심 화면 시안, 관련 테스트 및 단계·최종 보고.

### 제외

- Electron·React 교체 및 Scratch의 Tauri·편집기 도입.
- 프롬프트 실행·실행 결과 저장, 신규 시나리오·에이전트 추가.
- 자동 유지보수·스캔·LLM 호출, 무관한 기능·의존성 변경.
- 사용자 미커밋 변경 또는 기존 BMAD 설치의 무단 이동·삭제·커밋.
- 읽기 전용 `docs/plan/plan.md` 수정, 승인 없는 commit·push·PR·merge.

## 설계 방향

- 기존 로컬 컴포넌트 래퍼와 토큰을 갱신하며 별도 UI 시스템을 추가하지 않는다. 화면 수치·색상은 사용자 결정과 시안 검증으로 확정한다.
- Library의 사이드바·목록·컴파일러/상세 작업 영역은 항상 유지한다. 직접 편집·복사와 컴파일 동작의 관계는 Stage 1에서 명시하고 새 필수 패널을 추가하지 않는다.
- 창 드래그는 OS 창 동작을 사용하고 입력·선택·버튼 조작과 충돌하지 않게 한다. 지원 OS·Electron 옵션을 조사한 뒤 필요한 범위만 적용한다.
- 테마는 의미 기반 토큰으로 관리하고 창 배경·컨트롤·대화상자·잠금 화면까지 양 테마를 확인한다. 렌더러는 OS/Node API에 직접 접근하지 않는다.
- IPC 변경은 계약 → bridge 타입·구현 → handler → 서비스·저장 → 테스트 순서로 반영한다. DB 스키마 변경이 실제 필요할 때만 Drizzle과 migration을 함께 갱신한다.
- 저장은 기존 버전·복제 경로를 재사용한다. 수정한 현재 내용이 저장·복제·복사에서 어떻게 사용되는지 명확히 정의하고 중복 저장·동시 이동을 방지한다.
- 미저장 보호는 저장 성공을 확인한 뒤 이동·닫기를 재개한다. 삭제·잠금·앱 종료 등 추가 경계는 기존 보안과의 충돌 여부를 조사하고 정책 추가가 필요하면 확인받는다.
- bmad-ux의 Create 모드로 기존 디자인을 입력 자료로 사용하되, 새 색·레이아웃을 사용자 확정 없이 최종 계약으로 만들지 않는다. 기존 기준과의 차이를 명시한다.

## 잠정 단계

- **Stage 1 — UX 계약과 핵심 화면 확정**
  - 현재 앱을 안전한 테스트 데이터로 탐색하고 창·드래그·크기·입력 상태를 확인한다.
  - bmad-ux로 합의 사항을 memlog에 기록하고 미결정 항목·화면/사용 흐름 대응·접근성·테마를 정리한다.
  - Library·Settings·미저장 보호의 핵심 시안을 검토한다. 리뷰 렌즈는 사용자 opt-in으로 결정한다.
  - 공식 시각·행동 계약과 시안을 확정하되 승인 없이 제품 구현으로 넘어가지 않는다.
- **Stage 2 — 네이티브 창과 양 테마 기반**
  - 창 통합·정확한 드래그 경계·초기 크기·테마 저장 및 OS 변경 반영을 구현하고 검증한다.
- **Stage 3 — 작업 공간과 설정 정리**
  - 3패널 연결·목록/툴바·설정 분리·컴파일러 추가 옵션·사용자 문구를 갱신한다.
  - 화면 이동 후 선택·편집 상태와 Insights·Privacy 예외 동작을 검증한다.
- **Stage 4 — 직접 사용과 안전한 저장**
  - 직접 복사·편집·기본 새 버전·별도 복제 저장·미저장 보호를 완성한다.
  - 저장 오류·취소·버리기·반복 저장·전환 경계와 창 닫기를 검증한다.
- **Stage 5 — 통합 검증과 최종 보고**
  - 양 테마·창 크기·메뉴·키보드·전체 핵심 흐름·기존 기능 회귀를 검증한다.
  - 영향받는 안내와 QA를 정합화하고 최종 보고 후 별도 PR 승인 절차로 넘긴다.

## 검증 계획

### 단계별 검증

- Stage 1: 소스 관찰과 실제 재현을 구분해 기록, 화면별 journey coverage·기존 계약 충돌·시안의 양 테마 확인. 사용자 데이터 대신 테스트용 userData/DB를 사용한다.
- Stage 2: 테마 기본값·선택 persistence·OS 전환·재시작, 창 버튼/드래그와 입력 충돌, 초기/최소 크기의 패널 가시성·가로 넘침. 관련 IPC/설정/창 테스트.
- Stage 3: Library와 Settings 이동·상태 복귀, 검색·필터·옵션·잠금 화면·키보드 포커스, Insights/Privacy에서 자동 작업이 시작되지 않음. 관련 UI 테스트.
- Stage 4: 직접 복사 payload, 새 버전 번호·기존 버전 보존, 복제의 독립성, 저장·버리기·취소·저장 실패와 창 닫기. 관련 저장/bridge/UI 테스트.
- 각 구현 단계: 관련 focused tests, `npm run typecheck`, `npm run lint`, `git diff --check`. 필요한 native rebuild는 기존 native:node·native:electron 스크립트만 사용한다.

### 통합 검증

- `npm test`, `npm run build`, `npm run test:smoke`를 실행하고 실제 macOS 창 동작을 별도로 확인한다.
- 시스템 / 라이트 / 다크, 설정 재시작 유지, Library 3패널, 직접 복사·새 버전·복제·미저장 보호를 확인한다.
- 자동화로 증명하기 어려운 창 드래그·시각 일체감은 수동/시나리오 검증 근거를 명시한다. 실행하지 못한 항목은 통과로 보고하지 않는다.
- task31 worktree의 변경은 승인된 범위에 한정하고 `git diff --check`가 통과한다. 명시적 commit 승인 후 PR 준비 전에는 task worktree가 clean인지 확인한다.
- 주 checkout의 기존 사용자 미추적 파일은 유지하며 이번 task의 clean 기준과 구분한다.

## 리스크

- **기존 기준 충돌**: dark-only 및 의도된 가로 스크롤 규칙을 새 합의로 명시 개정하되 필수 3패널을 숨기는 방식으로 해결하지 않는다.
- **OS 드래그 원인 미확정**: 실제 앱을 재현한 후 Electron 창 옵션과 hit-test 경계를 판단한다. 웹 기술을 원인으로 단정하지 않는다.
- **편집·컴파일 상태 혼선**: 저장·복사 대상과 프로젝트 binding을 명확히 하고 설정 이동 또는 선택 변경에서 편집을 잃지 않게 한다.
- **닫기/잠금 보안 충돌**: 저장 확인을 위해 민감한 내용을 renderer나 로그에 추가 노출하지 않는다. OS 강제 종료까지 보장한다고 주장하지 않는다.
- **시크릿·유지보수 회귀**: 설정 이동이 raw key 노출이나 자동 scan 실행을 유발하지 않도록 기존 경계를 테스트한다.
- **BMAD 비추적 설치**: 작업 공간과 스킬 경로를 분리해 검증하고 사용자 설치를 제품 PR에 임의로 포함하지 않는다.
- **네이티브 모듈 환경**: Node와 Electron SQLite ABI를 구분하고 실제 실행 실패는 검증 한계로 기록한다.
- **남은 UX 결정**: 사용 대상의 stakes, working mode, 정확한 최소 크기, 직접 편집 화면 배치 등은 사용자 확인 또는 시안 검토 전 확정된 사실로 쓰지 않는다.
